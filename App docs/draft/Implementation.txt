Implementation
-------------------

Devices
--------------

- Restaurant Devices, devices designed for making customers order request.

- Employees like Manager, waiters normal devices.


Users
-----------

- Boss, boss is the user who has all control of the app and is the one to make server side configs, this user is not registered manually. He is only registered by the developer directly in the database.

- Customers, customer will user specific restaurant devices to make order request, and they're anonymous users in a right technical term, their order request will only be protected by a key generated by the Boss on the specific restaurant only devices.

- Manager, managers will have to be registered in the system by the Boss, it means boss will give them the passwords they will use and their username [emails].

- Waiters/Waitress, they will be registered in the system by managers or boss.

DTOs
------

- Product

- User

- Order

High level system flow
---------------------------

- Login activity, this UI will get the Username and password and they're sent to the server, in the server's response they will be all details about the logged in user.

	* This activity and the button that can be triggered to render it, will not be shown in the client that has in it the desired key in the Android Key Store. Because it means that this client is already designed to be for only customers who are making requests. 

So as the app launches it'll check for the key and checks if it's valid from the server if the answer is true then they will be no rendering for 'Login Button View' and it means that the login UI is no longer seen as well.

	* According to the server response about who is the user the app will display the desired buttons that can be triggered and render different activities.

- UI designed for creating a password that will be kept on the server and also be kept in Android Key Store, this UI is only designed to be shown to the registered user on the server who has ROLE of BOSS, because it's handling complex security feature for the app.

	* It's the UI that renders the CRUD operation of managing users with role manager. This allows the boss to have full control of his managers.

	* This UI will allow the boss to register the key that will be sent to the server as a header in a request when a customer clicks on 'Submit Order' button, this key is kept on server and also in android key store [client side].

So as the boss saves the key the server will store it in an encrypted way, u can use BCryptPasswordEncoder to encrypt it on the server side and u'll keep it as raw on the client side. 

This key is immutable and it must only be one, so it will be created by the boss user once and if done it'll just be shown in this activity otherwise the app will display a label that there's no key created for 'Customer Ordering' yet.

The key can also be deleted. But not updated.

This key is crucial because when customers make order request using the desired activity, the request is not secured it's just a permit all request, because customers don't need to provide their credentials when they need to order, so the key will be passed in the header so that the server knows that the desired client is the one making request. 

So this key will be inserted by the BOSS in specific devices that are allowed to make request to the server.


- UI rendering CRUD operation of products, the button triggering to this activity as well as this activity are to be shown if user is logged in and has ROLE of being either a Boss or a Manager.

	* The product creation will require a non null name, non null price, non null description and non null pictures.

These pictures will be stored under the drawable resource folder in the folder called restaurant products. Note that each product will have the folder named to it's name and this folder has the product pictures in it.

So the database will just store the path of the product pictures and the product's name must be unique as it's the identifier of the folder keeping the product's pictures.

Before the app save these pictures in the designed folder, the server must responds positively that the record is posted successfully (200) and also the server will not try to handle the product's name issue like doing like (Apples (1)) for conserving uniqueness instead it'll just responds (400) to the client so that the user finds another name herself explicitly.

The product fields can be modified [name, price ,description, images] by those users also, and the name if updated it must be also validated, if name is updated it'll change the folder name also.

The product can be also deleted and all of it's things are gone including folders.

This activity will show the products in a way they are shown on the customer ordering activity, but they will no ordering number text fields, add to order button (it means every view which is order specificity won't be there).

So u get that each product will have update button that will render the activity to update the product [which include product picture deletes, but should no be left null or folder empty],
and each product will be having a delete option for deleting it as well.

- UI rendering products so that user can submit order, the activity is only rendered when the client has in it the desired 'key' saved by the boss in the Android Key Store. 

It means after saving the key the boss will log out. If the app is opened again it'll show this activity only and they will be no 'Login' button view or any other view except the ones discussed below regarding this activity.

So at every start up of the app they must be the key check up which include calling server to validate the key [the retrieved key] and if valid this activity will show up. If it shows up the Login Page.

	* This interface shows all products information. [name, description, images, price], these information are to be shown as carousels, like for example Instagram Posts.

The carousel has also a text field that request the customer to enter the number of products he wants to order. (It only accepts numerics)

The carousel has also an 'Add To Order' button view. That will show error message if user has not specified the number of items he wants to order.
	
	* This interface has a button that can display an activity showing the items that the customer has picked for order.

 	The div works as follow:  if a customer adds a product to the order, the div will automatically append the new product on it and adds up the price to the total price, similarly if the product is removed then the div will remove that product from it and subtract the total price as well.

This div is in another activity, so the button to go to that activity is a shopping cartel that will also have a number on it which increase or decrease according to if user has added or removed a  the product. [The number is like the one on WhatsApp showing the unread messages, note that it's generated based on the ordered products]

	* This interface will have submit button, if it's clicked then it will show the receipt and ask the customer to confirm, if the customer confirms, the app will retrieve the key from the android key store, if the key is not there it'll throw an exception and UI will display unauthenticated user message, if everything is fine the flow continues to the server.

	* This interface should have a table number text field so that the customers will fill also the table number they're sit on, so that the waiter or waitress know which table requested.
So the order must go with this table number it must not be empty or null and it only accepts inputs numbers.	

	* This interface will have a text area where user can provide feedback on our restaurant service, note that this feedback will be sent with the key in the Android Key Store, in a same manner as the way making an Order is done. [it will be perfect is the text area and the button are at the end of the page]

	* As the server process this order and it's done successfully the server will produce a UUID which is a unique string that identifies the order uniquely in the database, so it'll be sent back to the user who has made the order into the device that they have used.

The button and the label shown on this interface are only shown when the user has made the order.

This is crucial because if a customer has made an order and maybe he waits for long he may hit the button to claim that the order is late, this feedback will go to the server and if the order is at least done 15 minutes ago then the server will make a web socket invocation to the Activity rendering orders that are late to be processed. 

Otherwise the server will tell the customer to be patient for at least 15 minutes, by showing the time the order being claimed to be late was processed and the remaining minutes so that the customer can actually claim.


-  UI rendering orders that are made by customers, this activity and the button that render this activity as well, will be shown for users who have roles: Boss, Manager, Waiter Or Waitress 
after they have logged in.

	* As server receives the customer's order, it will save this order in the database and then it'll notify the clients that render this activity, through a web socket. The notification from the server will make clients append this order. Like the way a chatting app receives server web socket call to render a chat.

	* This activity will simply display a table showing these columns, here are column titles: Order Number, Order UUID, Order Products, Order Total Price, Order Table [the table customers are sit on], Order is paid, Order Taken By, Take Order.

The table mentioned above isn't an all time table, it's a daily table. It means this activity has a sliding side panel that has today's dates, previous days dates ... where a user will click on a date and it'll render the table showing all data in the columns discussed above.

So it's understandable that when a new day comes at 00:00 the new button is appended at the top of the side panel and if clicked it shows new table. 

Note that the previous day table, can't no longer be appended with new rows as we're on a new day, so new rows goes to the current day table instead.

So the columns are actually showing the database record of order but the last 2 columns play crucial role.

The last column [Take order] will show a button view which is hit by user with only the role of waiter or the waitress so as server receive the request it will validate the user and if the user isn't waiter or waitress (find a name that fits the 2 terms please because they have same meaning in my app), the server will simply show the user invalid denying message.

So if the desired user has hit the button then this row will contain the username of the waiter who took that order and the button will be disabled so that no other waiter takes it.
So this transaction of taking or processing a user order should be a database SERIALIZABLE transaction for avoiding race conditions.

If the customer pays the Order then column showing if order is paid will be updated, the process of entering this payment and validating it is explained below.





- UI rendering orders that are late to be processed, this activity and the button that render this activity as well, will be shown for users who have roles: Boss, Manager, Waiter Or Waitress 
after they have logged in.
This activity will be showing orders that customers have claimed for but they're late to be served. So if a customer makes an order and after 15 minutes there's no waiter to give her the service she could claim and this failed order will be appended to the table in this activity.
	
	* First this failed processing order will be recorded in a database table for Waiter or Waitress failed processing order then it will remove the waiter and waitress who has taken this order from the 'Waiter or Waitress processed order table' (if present) then the server will return to the activity the waitress's username who has taken the order if present so that the order and the waitress username will be displayed in a table on this activity. But if no waitress has taken the order then the order only can be put in table and the waitress's username is left blank.

Next the server will call the activity UI that render orders that are made by customers via a web socket, to update the Order Taken By and Take Order column so that a new waiter or waitress can process the order and take it, this will be done if this order had no previous waiter who has taken it.

 



- UI designed for inputting order payment, this activity and the button that render this activity as well, will be shown for users who have roles: Waiter Or Waitress 
after they have logged in.

	* First this activity will have the input fields so that a waiter can insert his ID, the order UUID and the button confirming that the customer has paid the order, on the server side they must be validations to check if this order exists and that it's taken by the waiter who is confirming it's payment.
If valid then record this in the database table by updating the 'order paid column' in table Order.
